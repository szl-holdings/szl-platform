## What -04 is, verified from the text

The record **is** the envelope, normatively:

- **§4.6 verification order, §4.8 types.** A record is an in-toto Statement
  inside a DSSE envelope. `_type` MUST be `https://in-toto.io/Statement/v1`,
  compared byte-for-byte (vectors X4/X5 — a Statement whose type member is
  not those exact bytes is malformed). The verifier checks the exact bytes
  signed over RFC 8785 canonical JSON, never a re-serialization.
  §4.1.1 (new in -04): a number written with a fraction or exponent makes
  the Statement malformed whatever its value (vector X1).
- **§4.7 retention entries and anchors.** Retention claims verify offline:
  RFC 3161, transparency-log, or OpenTimestamps anchor kinds, with the
  7200-second confirmation tolerance for OpenTimestamps and upgraded-proof
  appending (both new in -04 per Document History).
- **§4.9 sets of records (new in -04).** A JSON `records` array of DSSE
  envelopes carried exactly as signed; malformed-record and
  malformed-set propagation is fail-closed; and, deliberately, the set
  "adds no signature and asserts nothing of its own" — no count, no
  digest, no completeness semantics.
- **§6.10 (new in -04).** A verifier checking a retained record never
  submits it to a live decision point or replay/nonce/consumption ledger,
  never reads present state as input, and a decision point never takes a
  retained record as authority for a new action. Retention verification
  cannot touch the producing system — offline verification as a security
  property, not just a capability.
- **§5 members.** evaluation, consumption, sequence, decision, retention,
  plus the -04 additions: §5.2.1 `principal` (a signed validated token,
  bound by digest to `agent.credentialDigest` and by issuer-key
  thumbprint, lifetime checked at `decision.reportedAt`; vectors
  PR1–PR11) and §5.2.2 `dataSubject` (whose data a call read, by keyed
  reference, distinct from the delegated principal, with purpose from the
  server's declared list; vectors DS1–DS10). §5.9 hardened
  (`operationKey` non-empty; `asset` for non-ISO-4217 denominations;
  `supersedes` for limit replacement while permits are held).
- **§8 predicate types frozen** (v1/v2 URIs); **§9 conformance** pinned to
  the agent-evidence-vectors corpus — 225 members this revision,
  CI-replayable, with two independent verifiers plus a third-party reader
  (MoltyCel/moltrust-api). The Document History credits 20+ named
  contributors, including two independent verifier runs against the
  corpus (J S He, Konrad Gruszka) — multi-implementer health unusual in a
  pre-WG individual draft.

## Assessment against SZL's standing positions

1. **DSSE-style envelopes — ADOPTED, normative.** Not a carriage option:
   the envelope is the record format; byte-exact `_type` checks and
   RFC 8785 canonicalization close the re-serialization hole (SZL runs
   the same discipline in `szl-receipt-dsse`).
2. **Chain digests + signed checkpoints — OPEN.** Each envelope is
   individually signed; §4.9 sets are honest about asserting nothing.
   There is no predecessor-digest chain, no set-level count/digest, no
   signed checkpoint. See request R1.
3. **Offline verification — ADOPTED, normative in substance.** §4.6/4.7
   verify locally; §6.10 makes retained-record non-replay a MUST; anchors
   carry verifiable proofs. See request R3 to pin the export-and-verify
   case in §9 conformance language.
4. **Memory governance — OPEN.** Member types govern tool/asset/data
   consumption and decisions, but no event class exists for writes to and
   recalls from persistent agent memory. `consumption` covers assets and
   API use (x402 / stablecoin cases, vendrell46's corrected rows), not
   memory. The Memory Covenant gap is unclaimed in this draft too.

## SZL requests (second-BoF-ready)

- **R1 — Signed completeness statement over §4.9 sets.** Keep the bare
  set exactly as defined (its "asserts nothing" honesty is correct for
  the transport). Add an OPTIONAL member/record type in the §8
  predicate-type registry: an envelope-carried completeness statement in
  the shape of [AAT-11 §8.5](2026-11-23-aat-11.md) — `record_count` +
  Merkle `set_digest` over the set's envelopes + declared scope +
  `as_of`, signed by the custodian who assembled the set. AAT-11 already
  defines the semantics of falsifiable absence and false-completeness
  evidence (AAT-11 §14.7); gilda-04 defines how enveloped records travel.
  The two AUDIT candidates converge before WG formation, and a set-level
  checkpoint removes the O(n) per-envelope verification burden for large
  exports. This is SZL standing-position material (envelopes + digests +
  offline verification) and slots into the charter's data-model
  deliverable.
- **R2 — Memory-governance member class.** First-class member types for
  governed memory writes and recalls, carried in the same DSSE envelopes.
  SZL offers the [Memory Covenant](https://github.com/szl-holdings/szl-frontier/tree/main/covenant-spec)
  as running-code reference: deny-by-default governed memory plane,
  hash-chained receipts, BFT witness countersigning, Lean-verified
  monotonicity lemma. No current AUDIT candidate covers this gap.
- **R3 — Pin offline verification in §9.** The practice exists (corpus
  is CI-replayable; reference reader refuses offline-unsafe operations;
  §6.10 forbids live-state reads). Ask that §9 state a conforming
  verifier verifies an exported set with no network access to the
  producing system — locking standing position 3 into conformance
  language rather than implementation custom.
